This chapter describes the implementation of the multi-agent fruit harvesting simulation. The system is built using Mesa 3.0, a Python framework for agent-based modeling. The implementation focuses on RQ1 (communication range effects) with Static resource dynamics only.

\section{System Architecture}

The system consists of three main components:

\begin{itemize}
    \item \textbf{Environment}: 50×50 grid world with fruit resources
    \item \textbf{Agents}: Mobile harvester agents with communication capabilities
    \item \textbf{Data Collection}: Metrics tracking and visualization
\end{itemize}

\subsection{Overall Structure}

The implementation follows Mesa's standard architecture:

\begin{itemize}
    \item \textbf{Model class} (\texttt{HarvestModel}): Manages the simulation
    \item \textbf{Agent classes}: \texttt{HarvesterAgent} and \texttt{Fruit}
    \item \textbf{Grid}: \texttt{MultiGrid} for spatial representation
    \item \textbf{DataCollector}: Tracks metrics at each step
    \item \textbf{Visualization}: SolaraViz for interactive display
\end{itemize}

\subsection{Model Class}

The \texttt{HarvestModel} class (in \texttt{src/models/harvest\_model.py}) manages the simulation. It inherits from Mesa's \texttt{Model} class and handles initialization, agent placement, fruit placement, and data collection.

\textbf{Constructor parameters}:
\begin{itemize}
    \item \texttt{width}, \texttt{height}: Grid dimensions (default: 50×50)
    \item \texttt{num\_agents}: Number of harvester agents
    \item \texttt{fruit\_density}: Proportion of cells with fruit (0.0-1.0)
    \item \texttt{comm\_range}: Communication range in cells (Chebyshev distance)
    \item \texttt{seed}: Random seed for reproducibility
\end{itemize}

\textbf{Key methods}:
\begin{itemize}
    \item \texttt{step()}: Executes one simulation step using Mesa 3.0's \texttt{shuffle\_do('step')} for randomized agent activation
    \item \texttt{run\_model(steps)}: Runs the model for a specified number of steps
    \item \texttt{\_place\_fruits()}: Randomly places fruit on the grid according to density (Static dynamics only)
    \item \texttt{\_place\_agents()}: Randomly places harvester agents on the grid
    \item \texttt{\_get\_total\_yield()}: Calculates total fruit harvested across all agents
    \item \texttt{\_get\_messages\_this\_step()}: Counts messages sent in current step
    \item \texttt{\_get\_remaining\_fruit()}: Counts available fruit on grid
    \item \texttt{\_get\_coverage()}: Counts unique cells visited by all agents
\end{itemize}

The model uses Mesa's \texttt{DataCollector} to automatically track metrics at each step, including total yield, messages sent, remaining fruit, and coverage.

\subsection{Grid and Spatial Representation}

The environment is a 50×50 grid with non-toroidal boundaries (implemented using Mesa's \texttt{MultiGrid} class). Non-toroidal boundaries create realistic edge effects where agents near boundaries have fewer neighbors, which is appropriate for a harvesting scenario where the field has physical boundaries.

The \texttt{MultiGrid} class allows multiple agents to occupy the same cell, which is necessary since both harvester agents and fruit resources share the grid. The grid uses standard Cartesian coordinates with (0,0) at the bottom-left corner.

\subsection{Harvester Agent}

The \texttt{HarvesterAgent} class (in \texttt{src/agents/harvester\_agent.py}) implements agent behavior. Each agent maintains:

\begin{itemize}
    \item \texttt{pos}: Current position on grid
    \item \texttt{harvested}: Count of fruit harvested by this agent
    \item \texttt{messages\_sent}: Number of messages sent this step
    \item \texttt{messages\_received}: Number of messages received
    \item \texttt{current\_target}: Target fruit location (if any)
    \item \texttt{visited\_cells}: Set of unique cells visited (for coverage metric)
    \item \texttt{travel\_distance}: Total distance traveled
\end{itemize}

\subsubsection{Agent Behavior Algorithm}

The agent's \texttt{step()} method executes the following sequence:

\begin{enumerate}
    \item \textbf{Move}: Move to adjacent cell (Moore neighborhood, 8 directions)
    \begin{itemize}
        \item If agent has a target: move one step toward target using greedy movement
        \item Otherwise: perform random walk to adjacent cell
    \end{itemize}
    \item \textbf{Harvest}: Check current cell for fruit and harvest if available
    \item \textbf{Communicate}: Broadcast nearest known fruit location to neighbors within communication range
\end{enumerate}

\textbf{Movement Details}: The \texttt{move()} method uses greedy movement toward targets (moving in the direction that minimizes Chebyshev distance). If the target is reached, it is cleared. Random walk uses Mesa's \texttt{get\_neighborhood()} method with Moore neighborhood.

\textbf{Harvesting Details}: The \texttt{harvest()} method checks the current cell for fruit using \texttt{get\_cell\_list\_contents()}. If fruit is found and available, it calls the fruit's \texttt{harvest()} method to mark it as unavailable. The agent then clears its target.

\textbf{Communication Details}: The \texttt{communicate()} method finds neighbors within communication range using \texttt{get\_neighbors()} with Chebyshev distance (Moore neighborhood with radius parameter). It broadcasts the nearest available fruit location to neighbors that don't already have a target. Each message sent increments the agent's \texttt{messages\_sent} counter.

\subsection{Fruit Agent}

The \texttt{Fruit} class (in \texttt{src/agents/fruit.py}) represents harvestable resources. For RQ1, the implementation uses Static dynamics only (no regeneration). Key properties:

\begin{itemize}
    \item \texttt{available}: Boolean flag indicating whether fruit can be harvested
    \item \texttt{is\_fruit}: Marker attribute to distinguish fruit from agents
    \item \texttt{times\_harvested}: Counter tracking harvest attempts
\end{itemize}

\textbf{Static Dynamics}: Once a fruit is harvested, it becomes permanently unavailable for the rest of the simulation. The \texttt{harvest()} method sets \texttt{available = False} and increments \texttt{times\_harvested}. The fruit's \texttt{step()} method is a no-op (does nothing) for Static dynamics, included only for Mesa compatibility.

\section{Data Collection}

The system uses Mesa's \texttt{DataCollector} class to automatically track metrics at each simulation step. The model defines reporter functions that calculate metrics on-demand.

\subsection{Metrics Tracked}

The system tracks the following metrics at each step:

\begin{enumerate}
    \item \textbf{total\_yield}: Cumulative fruit harvested by all agents
    \item \textbf{messages\_this\_step}: Messages sent in current step
    \item \textbf{cumulative\_messages}: Total messages sent since simulation start
    \item \textbf{remaining\_fruit}: Count of available (unharvested) fruit on grid
    \item \textbf{coverage}: Number of unique cells visited by all agents combined
\end{enumerate}

These metrics are calculated by reporter functions in the \texttt{HarvestModel} class and collected at each step via \texttt{datacollector.collect(self)}. The collected data can be accessed as a pandas DataFrame for analysis.

\section{Experimental Infrastructure}

\subsection{Batch Experiment Runner}

The batch experiment runner (in \texttt{scripts/run\_experiments.py}) automates the 400 experimental runs:

\begin{itemize}
    \item Generates all 20 configurations (5 ranges × 2 team sizes × 2 densities)
    \item Runs 20 replications per configuration with fixed seeds (0-19)
    \item Saves results to CSV with timestamp
    \item Tracks progress and execution time
\end{itemize}

The runner creates a \texttt{HarvestModel} instance for each configuration and replication, runs it for 500 steps, and collects final metrics. Results are saved to \texttt{results/experimental\_results\_[timestamp].csv}.

\subsection{Reproducibility}

Fixed random seeds (0-19) ensure reproducibility of results. Each configuration-replication pair uses a unique seed, allowing the same results to be regenerated by running the experiment with the same seed sequence. Mesa 3.0 handles seed management through the model's \texttt{seed} parameter passed to the parent \texttt{Model} class.

\section{Implementation Notes}

\subsection{Mesa 3.0 API}

The implementation uses Mesa 3.0 API conventions:

\begin{itemize}
    \item Agent constructors take only \texttt{model} parameter (no \texttt{unique\_id})
    \item Agent activation uses \texttt{model.agents.shuffle\_do('step')} for randomized order
    \item Visualization uses \texttt{SolaraViz} with model instance
    \item \texttt{DataCollector} uses reporter functions for metric calculation
\end{itemize}

\subsection{Design Decisions}

\textbf{Chebyshev Distance}: Communication range uses Chebyshev distance (max of absolute differences) rather than Euclidean distance. This is appropriate for grid-based environments where agents move in 8 directions (Moore neighborhood).

\textbf{Greedy Movement}: Agents use greedy movement toward targets (moving in the direction that minimizes Chebyshev distance). This is simple and interpretable, though not optimal for all scenarios.

\textbf{Selective Broadcasting}: Agents only broadcast to neighbors that don't already have a target. This reduces unnecessary communication and focuses information sharing on agents that can act on it.

\textbf{Static Dynamics Only}: For RQ1, the implementation uses Static resource dynamics (no regeneration). This simplifies the analysis and allows clear focus on communication range effects without confounding factors from resource dynamics.
